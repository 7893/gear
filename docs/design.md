# 设计草案

本文保留设计概览；业务细节以[统一业务规则](business-rules.md)为准。部署分工见[技术选型与部署记录](technical-proposal.md)，不再制作样稿。

详细内容见[页面、字段与单据](screens-and-forms.md)及[技术选型提案](technical-proposal.md)，新增设计均为待审阅提案。

## 页面

尽量保留三个主入口：

| 入口 | 内容 |
| --- | --- |
| 设备台账 | 搜索、状态筛选、当前持有情况、设备详情和流转历史 |
| 流转办理 | 领入、分发、转交、退回，支持多设备一次办理 |
| 单据记录 | 查询编号、打印、上传签字件、核对归档、待回传列表 |

统计和到期提示可放在台账顶部，人员、团体与位置采用轻量选项维护，不必各做复杂模块。

## 最小数据

| 对象 | 建议记录 |
| --- | --- |
| 设备 | 唯一编号、名称、分类、品牌型号、序列号（如有）、来源批次、当前位置 |
| 接收对象 | 个人或团体、姓名或名称、所属单位、接收负责人、人员类型 |
| 流转单 | 内部编号、类型、交接日期、交出方、接收方、设备明细、备注 |
| 使用分配 | 设备、使用人或团体、开始日期、预计归还日期、实际结束日期 |
| 签字附件 | 所属单据、原始文件、上传时间、识别结果、核对结果 |

设备编号标识一件设备，单据编号标识一次交接；一张单据可包含多件设备，一件设备可关联多张历史单据。

详细关系、存量建账、当前分配和时间字段见[最小数据关系设计](data-model.md)。这是逻辑模型提案，尚未决定物理表结构或创建数据库。

## 状态口径

为避免把“在哪里”和“是否损坏”混为一谈，底层区分：

- 管理状态：在管、已退上游、遗失、已报废，互斥。
- 在管设备当前持有方：经办人库存、个人或团队；退出在管后保留最后责任方及处置记录。
- 设备状况：正常、故障，与持有关系分开。
- 单据有效性：草稿、已确认、已作废。
- 凭证归档：待回传、待核对、已归档。

界面可以组合显示“在库可用”“使用中”“在库故障”等易懂标签。设备转交不清除历史，人员离开也不删除其领用记录。

## 单据与打印

- 建议正式确认时生成唯一单号，格式示例：`LR-20261016-001`，最终前缀与流水规则待定。
- 重打保持原编号，作废编号不再使用。
- 已确认采用通用 A4 打印模板，单位名称可设置；模板含标题、编号、日期、交接双方、设备清单、备注、签字栏。
- 多页显示同一单号和页码，可通过浏览器保存 PDF。
- 确认后的交接信息不能任意覆盖；录错通过作废或更正留痕。
- 存在后续流转时，不能简单撤销早期单据导致当前台账失真。

## 一致性与识别

- 同一设备同一时刻只有一个有效持有关系。
- 提交确认应同时记录流转与更新台账，重复点击不能重复开单。
- 故障设备未经处理确认不能作为正常可用设备再次分配。
- 归还期限变化不等于设备交接，实际归还需明确登记。
- 识别优先解决“这张纸属于哪张单”，不默认承诺准确转写手写姓名或验证签名真伪。
- 上传附件本身不修改设备去向，归档由经办人核对确认。

## 运维边界

已确定互联网使用、约十名系统用户、允许云服务、电脑操作为主，以及源码公开开源。当前分工采用现有美国主机与 CloudFront 承载前端、亚太 Supabase 承担账号与业务后端；应用语言已确认为 TypeScript，前端当前推荐 Vue 3 + Vite，搭配 Element Plus 与 Vue Router，具体组合见[技术记录](technical-proposal.md#开发语言与前端方案)。OCR 服务和后台网关细节尚待确定。公开 GitHub 仓库已建立并关联，尚未部署设备簿应用。

### 针对已确认边界的设计建议

- 采用登录后访问的应用，数据库和签字附件不因源码公开而开放匿名访问。
- 使用独立账号记录操作人；管理员、经办人、查询人三种角色及全台账可见范围已确认，详见需求文档。采用账号密码登录，开放注册但须管理员审核。
- 多人同时办理时检查设备当前持有关系，避免同一设备被重复分配；单号生成需保证并发下唯一。
- 优先优化电脑端表格、批量操作和打印；手机支持查询与拍照上传已确认。
- 仓库仅保留源码、文档和虚构示例数据，不纳入实际台账、签字附件、数据库备份或服务凭据。
- 备份按最新决定简化，短期可暂不启用，后续按需手动整体导出；早期每日自动备份、30 天恢复点及一天数据损失窗口不再作为当前要求。
- 公开远程仓库已建立，开源许可证待选择；自动部署后续单独配置。

## 注册审核与邮件

- 账号状态分为待审核、已启用、已拒绝、已停用；待审核用户只能查看审核状态，不能查询台账或附件。
- 申请人不能自行授予角色；管理员审批时分配角色，默认查询人。
- 先验证注册邮箱再通知管理员审核，审批结果通知申请人；临时使用的归还提醒按统一业务规则执行。
- 邮箱验证、密码找回、首次管理员初始化和停用处理的核心流程已确认，见[账号流程](account-design.md)；尚未实现，具体安全参数待定。
- 管理员重置密码应使用一次性重置流程，不查看或发送用户原密码。
- 邮件发送失败应可追踪和重试，不回滚已经完成的审核或流转操作。

## 选型约束

- 当前以尽量零新增费用为目标，优先免费产品与复用现有资源。
- 免费额度、产品限制和价格在正式选型时查证，不将当前草案视为零费用承诺。
- 同时考虑约十名用户、签字附件增长、手动导出和邮件发送的用量。
- TypeScript 开发语言已确定；前端框架及组件组合、OCR、后台代理细节与开源许可证尚待确定，云资源和配置修改仍需逐项授权。
- Supabase 仅免费版，CloudFront 使用 Free 套餐；Oracle 若使用仍限永久免费资源。保活已有方案，不作为排除平台的依据。前端境外托管，国内完整访问待实测；早期付费及自动备份建议以最新记录为准。
