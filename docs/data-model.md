# 最小数据关系设计

状态：依据已确认业务整理的逻辑模型。已在共用亚太 Supabase 项目的独立 `gear_2026` schema 建立表结构、权限基础及账号事务 RPC，隔离验证及云端元数据复查通过；存量建账及台账查询接口已随迁移 005 获授权上线，领入、分发、退回及打印已获授权上线，迁移 006 已应用、独立开关开启；完整业务验收尚未完成。字段与实施范围见[数据库模式设计](database-schema.md)及[账号实施记录](account-implementation.md)。

## 1. 逻辑对象

| 对象 | 主要内容 | 关联 |
| --- | --- | --- |
| 设备 | 内部标识、展示编号、旧编号、名称分类、型号、序列号、管理状态、状况和位置 | 一件设备关联多条单据明细、使用分配及事件 |
| 人员与团队 | 姓名或团队名、对象类型、团队默认负责人、人员类型、是否停用 | 作为交接双方和责任人；可选关联登录账号，不要求注册 |
| 交接单 | 类型、正式单号、实际交接日期、双方及负责人快照、抬头、草稿/确认/作废状态、经办账号 | 一张单包含多条明细，可关联多个签字附件 |
| 单据明细 | 设备内部标识、确认时编号和资料快照、交接时状况及必要备注 | 一行一件设备，不能只记同型号总数量 |
| 使用分配 | 设备、个人或团队、当前责任人、团队具体使用人、实际开始/结束日期、临时期限、是否有效、来源记录 | 一件设备最多一条当前有效分配；存量分配可来自建账事件 |
| 附件 | 私有存储对象标识、原文件名、类型大小、校验值、上传人及时间、识别和核对结果 | 明确归属一张单据或一条事件，支持建账凭证及故障等证明 |
| 设备事件与审计 | 事件类型、设备、实际发生日期、记录时间、前后值、原因、操作账号、关联单据 | 保存建账、交接、延期、故障、退出管理及更正，不要求每条事件都有交接单 |
| 系统账号 | 认证主体标识、邮箱、显示姓名、联系手机号、邮箱验证状态、业务状态、角色 | 手机号仅作未验证联系资料；记录系统操作人，与实物接收人分开 |
| 待发通知 | 事件关联、收件账号或邮箱、通知类型、计划时间、状态、尝试次数和服务返回标识 | 按业务事件和周期去重；保留失败与结果不明，供管理员处理 |

以上为逻辑对象，当前[物理设计](database-schema.md)收敛为已创建的十一张表，[初始迁移](../database/README.md)随仓库保存。设备分类和位置先用轻量字段或选项；单位抬头和少量参数采用统一设置，不增加独立业务模块。

## 2. 当前持有关系

- 在管设备有一条有效使用分配时，持有方为该个人或团队；在管且没有有效分配时，属于经办人库存。
- 经办人库存是一个固定逻辑库存，多名系统经办人不形成多个仓库。办理人、实际交接双方、团队责任人分别记录。
- 非在管设备由管理状态和退出事件说明去向：已退上游记录接收单位和人，遗失/报废保留最后责任方，不能因没有有效分配而显示为库存。
- 团队分配必须有当次责任人；团队名册默认负责人只是后续填表参考，变更名册不能自动改写有效分配或历史单据。
- 团队负责人交接关联原团队分配并记录责任变化；原使用起始事实和期限不因换负责人而自动重置。
- 团队具体使用人可为空，补录、更换或清空只改变当前分配的使用人，保留团队和负责人，不生成交接单；个人直接持有时显示本人。按对象 ID 区分直接持有、负责团队设备及具体使用，不能按同名合并。迁移 017 已本地实现，尚未上云，见[实施记录](holdings-tasks-implementation.md)。

展示状态从设备管理状态、状况及当前有效分配组合计算，按统一规则形成六类互斥统计，不再维护一套可独立编辑的“页面状态”。

## 3. 单据、分配与历史

- 一个单据可以包含多类设备，同一设备在同一张有效单据中只出现一行；设备在其他历史单据中可以再次出现。
- 草稿不创建有效分配、不占库存。确认时核对设备及版本，在一次业务事务中写入正式单号、明细快照、设备变化、分配起止、设备事件和必要待发通知。
- 新领入、分发、转交及退回按既定规则处理；分发建立分配，接收对象变化的转交结束旧分配并建立新分配，退回只结束选中设备的分配，其他未退设备不受影响。团队负责人交接按上一节保留原使用事实。
- 存量设备直接按现状建账；已经在用的设备建立当前分配，未知实际开始日期留空，来源关联建账事件，不伪造旧交接单。
- 延期修改当前期限，同时写入原日期、新日期、原因及操作记录；已确认单据中的原期限快照保持不变。
- 遗失或报废结束当前有效分配和提醒，保留分配及最后责任方历史；找回根据实际持有情况重新确认，不能自动恢复旧期限。
- 打印以确认时快照为准，不直接拼接人员名册或设备主记录的最新名称。人员停用、设备资料更正和单位抬头变化均不能改变已签单据。
- 作废和更正按后续依赖检查执行，不做物理删除或自动批量重放整条历史。

## 4. 附件与通知

附件上传、识别、人工归档与后台邮件发送分别处理，失败不回滚真实设备流转。后台通知在业务事务提交后发送；上传文件本身不能创建或改变使用分配。

原文件留在私有存储，业务库只记录对象标识和核对资料，不保存长期公开下载地址。读取时由后端根据当前账号权限授权。替换已归档文件保留旧版本及更正关联，不因替换或备份过期自动删除业务原件。

识别结果保留候选单号与处理结果，人工确认才改变归档状态。通知发送前检查关联事件仍适用；恢复备份后不自动补发历史邮件。

## 5. 时间字段

按[统一时间口径](business-rules.md#11-时间口径已确认)区分两类信息：

- 创建、确认、上传、审核、修改、发送尝试等时间点使用 UTC，并以明确带时区的格式在接口中传输。
- 实际交接日期、预计归还日期等日期字段只保存日期；历史未知日期允许为空，不能用记录时间代替。

同一业务日期内以系统事件顺序区分多次交接，不能只按日期排序；UTC 时间点和业务日期均保留自身语义。

## 6. 一致性与开源边界

实现时需要验证的约束包括：内部标识及正式编号唯一、单据设备明细不重复、同一设备最多一条有效分配、团队责任人完整、草稿不改变持有关系、正式确认与当前状态及历史同步。

认证账号和业务角色关联明确，角色只能通过管理员受控操作变更。对并发设备办理、账号审核及最后管理员保护进行服务端验证，不以页面校验代替。

共享 Auth 身份与设备簿成员分别判断。已有认证身份不自动获得本应用权限；审核、停用和角色仅作用于设备簿。其他应用的同项目会话也须通过本应用成员检查。新表与 SQL 函数使用独立 schema，附件使用独立私有桶，详见[部署记录](technical-proposal.md)。

结构定义、迁移脚本及虚构示例可以公开；真实人员、台账、存储对象、附件和运行日志作为私有业务数据维护，不加入仓库或公开初始化数据。

## 本地扩展：凭证、纠错、导入与到期通知

迁移 018—021 未上线，不新增业务表。附件继续以 `document_id` 或 `event_id` 二选一关联，事件材料不改变原建账快照；核对记录追加留痕。管理员处置纠错使用 `asset_lifecycle_corrected` 和唯一 `reverses_event_id` 恢复原状态/分配，原事件永久保留。`assets_imported` 记录整批请求和原结果，逐行仍经过已有建账接口。

设置新增 `due_mail_enabled`（默认关闭）、`due_mail_enabled_at`；原提前天数和本地时间继续复用。`daily_due` 使用原通知队列，按业务日与收件成员去重，发送前重算当前资格和数量。原件和应用模式的备份不包含共享认证密码，恢复验证原身份并关闭通知，详见[实施记录](completion-implementation.md)。
