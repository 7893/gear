# 设备转交与团队负责人交接

状态：已获授权上线，迁移 010 已应用正式数据库，页面通过本轮既有 CI/CD 发布。本轮不办理线上演示或真实交接，也不把虚构文件回执视为真实签字件验收。

## 业务行为

“流转办理”增加“新建转交单”，在现有交接表单内选择方式，复用来源、接收对象、设备勾选、草稿、确认、打印和签字件归档。

| 方式 | 前提 | 当前分配与设备 |
| --- | --- | --- |
| 更换持有方 | 同一当前持有方及交出负责人；设备在管且正常；接收方不同且有效 | 结束所选设备的旧分配，为新个人或团队建立新分配，重新确定长期或临时期限 |
| 同团队负责人交接 | 同一团队、不同负责人；新负责人有效；设备仍在管 | 只修改所选设备的责任人，保留分配身份、来源、实际起始日期、长期或临时方式、原期限及跟进经办人，故障状况不变 |

团队默认负责人不随交接自动变更，未选择设备不改变。负责人交接可在一单中包含不同期限、未知起始日期、长期使用及故障设备；逾期日期保留，不借责任交接清除逾期。普通转交的不同期限应分单。

界面先选择当前持有方和交出负责人，再选接收方或新负责人。正常转交仅列可转交的正常设备；负责人交接展示原起始日期及各件归还期限，交接状况按当前状况只读带出。故障交接保留简短说明，后端拒绝把故障改为正常。

草稿不改变设备去向。确认时重新核对设备版本、实际持有与责任关系、接收人和业务日期，整单一次提交；旧期限延期后保存的旧版本草稿必须重新核对。相同请求重试返回同一结果，不重复开单；不同请求争用同一设备时只允许一项成功。

转交已确认采用已有设计的 `ZJ-YYYYMMDD-0001` 格式，与领入、分发、退回共用确认当天的东八区日流水，至少四位自然扩展；这项前缀已随本轮上线范围确认。交接实际日期和记录时间沿用现有口径。

## 共用实现

- [迁移 010](../database/migrations/202610190010_transfers.sql)扩展原有两个私有函数：`save_document` 与 `confirm_document`。公开 RPC、参数签名、对象身份、所有者、执行权限和其他函数保持不变，不增加表、列、触发器、角色、密钥或事件类型。
- 保存与确认仍走同一事务实现，复用锁顺序、取号、版本校验、重试、快照和事件。历史迁移不改写；010 在事务内核对前一版函数体指纹，遇到未知修改或重复执行安全失败。
- 前端扩展同一个 `DocumentFormView` 和 `flows-model`，接收对象与来源控件各保留一份；操作区使用公共 `ActionGroup`。单据列表和筛选读取共用类型表。
- 正式打印使用同一个 `DocumentDetailView`，打印转交方式、新旧负责人和冻结资料。负责人交接逐件列出原起始日期与归还期限，使用保存的快照，不读取当前名单或期限重建旧单。
- 确认后使用已有二维码、原件服务、人工核对与归档接口。识别和签字真实性的边界不因新增单据类型而扩大，见[签字件实施](evidence-implementation.md)。

## 检查与上线边界

[数据库隔离检查](../database/tests/check_transfers.py)验证函数身份与权限保留、重复迁移拒绝、个人与团队间的部分转交、幂等及竞争、混合期限与故障责任交接、无效接收人、混合来源整单回滚、延期版本冲突、旧负责人不能退回、新负责人可部分故障退回，以及冻结快照。复用已有附件检查辅助函数，以虚构服务端回执验证转交单可走预留、完成和人工归档，不访问实际文件或云端 Storage。

[浏览器检查](../web/tests/flows.spec.ts)新增普通转交与新期限、确认重试、混合故障与期限的责任交接、相同负责人拒绝、只读查看和冻结打印的覆盖；本轮新增四个场景，连同既有账号、附件、台账、延期及公共控件共四十九个场景。正式库权限、匿名拒绝与现有单据只读查询已核对；真实登录、纸张签字及大陆网络仍待本人验收。

本轮已获单独授权，先核对函数指纹并保存云端基线，再应用迁移 010，确认只改变两个指定函数体，随后通过既有 CI/CD 发布页面。原有五十一台设备、三张单据、编号、权限和共享配置保持不变；技术上线未办理业务转交。网站 CD 不执行 SQL；新页面依赖新迁移，不能先推送发布。上线技术检查只执行只读查询，不自动转交设备或制造签字件。

回退页面可发布上一版本；新保存的转交草稿或正式单据必须保留。若已经产生转交数据，不能直接恢复旧保存/确认函数或删除新类型记录；数据库回退需按实际数据单独设计和授权。真实身份、地址、资源标识及云端原始记录只保存在已忽略的私有文件中。
