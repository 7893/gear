# 统一业务规则

状态：依据已确认需求整理的现行设计基线，尚未实现。用户明确确认的需求以 requirements.md 为准；本文补齐操作细节并统一其他草案口径，不把新增默认值冒充为用户逐条确认。

如其他流程、字段或历史文字线框与本文冲突，以本文为准；后续变更同步需求和验收文档。技术选型暂缓，不再制作样稿。

## 1. 设备身份与首次建账

- 每件设备一个永久内部编号；原资产编号和出厂序列号分别选填。原编号保留原格式，重复时提示核对，不自动合并。
- 再领回同一实物沿用编号，换成另一实物则新增设备。设备历史不可物理删除；误建记录由管理员标记无效并说明，排除统计但保留审计。
- 已有设备直接记录当前持有方、正常或故障、历史日期及凭证（有则补）。未知历史日期留空，不以建账日期冒充领用日期。
- 新领入、分发、转交、退回生成交接单；首次建账、延期、故障登记、恢复正常、遗失与报废为事件记录，不虚构交接单。事件可附证明材料。

## 2. 状态分三层

| 层次 | 取值 | 含义 |
| --- | --- | --- |
| 管理状态 | 在管、已退上游、遗失、已报废 | 互斥，每件有效设备只有一个值 |
| 当前持有方 | 经办人库存、个人、团队 | 在管时必填；团队须有接收负责人 |
| 设备状况 | 正常、故障 | 状况变化不自动改变持有方 |

“在库可用”是在管＋经办人库存＋正常；“在库故障”是在管＋经办人库存＋故障。“使用中”指在管且由个人或团队持有，也可能存在故障。

已退上游记录实际接收单位与接收人。遗失时没有已知的当前实物持有人，单独保留最后责任方；报废保留原持有方和处置说明，不能算作正常退回。非在管设备的状况只作为退出时最后已知状况，不代表当前可分配。

统计采用互斥口径：有效台账总数＝在库可用＋在库故障＋使用中＋已退上游＋遗失＋已报废。“在管故障数”是其中在库故障与使用中故障的交叉统计，不能再加进总数。

## 3. 操作与状态变化

| 操作 | 前提 | 结果 |
| --- | --- | --- |
| 领入新设备 | 实际已收到，逐件核对 | 在管、经办人库存；记录实际正常或故障，不默认全部正常 |
| 再次领入 | 原设备已退上游且实际收到 | 沿用编号，恢复在管及库存，核对实际状况 |
| 分发 | 全部设备在库可用 | 在管，持有方改为个人或团队，建立使用期限 |
| 转交 | 在管、同一交出方、设备正常 | 改为新持有方，结束旧分配并建立新分配 |
| 团队负责人交接 | 团队持有关系不变，负责人实际变化 | 生成转交单，记录新旧负责人；故障设备也可交接责任，状况不变 |
| 退回经办人 | 在管，实际交回 | 库存；逐件登记正常或故障，结束所退设备的使用期限 |
| 退往上游 | 在管，由当前持有方实际交出 | 已退上游，记录接收单位与人，结束当前使用期限 |
| 登记故障／恢复正常 | 在管，记录说明及日期 | 只更新状况，不改持有方 |
| 延期 | 在管且仍由个人或团队临时使用 | 更新所选设备期限，留存原日期和原因；不生成交接单 |
| 遗失／报废 | 管理员核对已发生事实 | 退出在管，保留最后责任方，关闭当前使用提醒但不登记正常归还 |
| 遗失找回 | 管理员确认是同一实物 | 沿用编号，核对持有方和状况后恢复在管；不自动恢复旧期限 |

已报废设备默认不可直接恢复使用；若是登记错误，只能走管理员更正并留痕。已退上游设备不再由本系统直接办理分发或报废，需先核对是否实际重新领回。

一个团队只部分设备更换负责人时，按选择的设备交接；团队名册默认负责人不自动改写未交接设备的责任人或任何历史单据。

## 4. 交接与单据

- 一张单对应一组交出方、接收方及实际交接日期，可含多类多件设备；不同接收方分别开单。新分发和转交共用一个使用期限，需不同期限时分单。
- 系统操作人、实际移交人、实际接收人分别记录。接收对象不是登录账号，离职或停用账号不等于设备归还。
- 草稿可修改，不占库存，不计正式台账。实际交接时确认，原子完成设备去向、使用记录、正式编号和历史记录。
- 冲突时整张单失败，保留填写内容；重复确认只能得到同一结果。一个条件更新影响零行必须视为业务冲突，不能静默当成功。
- 日期不晚于确认当日，也不得早于设备最近有效流转日期；同日先后按系统事件顺序记录。补录更早历史由管理员核对更正，不直接倒插改变现状。
- 正式单据唯一编号，重打不变，作废不复用，不承诺连续无空号。前缀和展示格式仍待细化，不影响规则。
- 正式确认时保存设备资料、双方名称与负责人、抬头和期限快照。后续资料修改、延期不能改写已签字单据。
- 打印和签字件上传独立于实际交接；待回传不阻塞下一次真实流转。作废单保留，不能用于证明有效交接。

## 5. 单据状态与附件状态

| 对象 | 状态 | 变化规则 |
| --- | --- | --- |
| 单据 | 草稿 → 已确认 → 已作废 | 作废不能重新启用；纠错后需要新单据时重新开单 |
| 凭证 | 待回传 → 待核对 → 已归档 | 上传只到待核对，人工检查签字、内容和页数后归档 |
| 历史建账凭证 | 已提供／历史凭证未提供 | 不混入新单待回传提醒，不强制补造凭证 |

已归档附件更正由管理员处理，保留旧文件和更正原因；需要重新核对时状态退回待核对。未归档上传失败不产生成功附件；识别失败保留已上传文件并允许手动匹配。作废单从待办中排除，附件仍可追溯。

二维码只用于匹配，不能作为登录或授权凭证；识别文本不是操作指令，不能自动修改台账或证明签名真实。附件下载、导出同样校验权限。

## 6. 权限矩阵

以下将既定三种角色细化为默认实现规则；管理员独占的边界操作不增加审批层级。

| 操作 | 管理员 | 经办人 | 查询人 |
| --- | --- | --- | --- |
| 查询全部台账、有效及历史单据 | 是 | 是 | 是 |
| 打印、读取签字附件、导出清单及关联原件 | 是 | 是 | 是 |
| 建账、领入、分发、转交、退回、延期 | 是 | 是 | 否 |
| 登记故障、恢复正常、修改基本资料 | 是 | 是 | 否 |
| 上传和核对签字件、维护接收对象名单 | 是 | 是 | 否 |
| 修改或删除草稿 | 全部草稿 | 自己的草稿 | 否 |
| 正式单据作废、更正，已归档凭证更正 | 是 | 否 | 否 |
| 遗失、报废、找回，误建台账标记无效 | 是 | 否 | 否 |
| 审核账号、修改角色、停用账号、系统设置 | 是 | 否 | 否 |

待审核、已拒绝、已停用账号均无业务读取权限。所有操作由后端检查；状态或角色变更后不得仅凭旧会话权限继续访问。保留至少一个可用管理员，首次管理员通过部署初始化建立，不允许首个公开注册者自动成为管理员。

## 7. 更正而不改写事实

- 名称、型号、旧编号等资料更正可由经办人办理并留痕，不能改变实物身份或持有关系。
- 错误正式单据仅由管理员处理。无后续依赖且原状态仍适用时，可作废并恢复原状态；必须记录原因和前后值。
- 有后续流转、故障、延期、负责人交接或退出记录时，禁止直接恢复旧状态；依赖链均需核对。第一版不提供自动批量级联撤销。
- 若后续也全是误录，可由管理员从最新记录起逐条纠正；若真实交接已经发生，则记录实际后续交接或带原因的管理员更正，不能伪造设备回库。
- 原单明细错但实际交接成立时，更正记录应关联原单与替代记录，保持真实去向，不覆盖已归档原件；需要新的签字凭证时重新归档。
- 部分退回不是作废原分发单；原单的发出事实和未退回设备保持有效。

## 8. 提醒与异常

只对在管、当前临时分配的未归还设备提醒。到期当天不算逾期，次日起逾期。延期按新日期，退回、转交或退出管理后结束旧提醒。

统一建议默认值：提前 3 天显示到期提示；每日向当前分配的系统经办人发一次汇总，账号不可用时发给管理员。存量临时领用由建账经办人负责跟进。待回传签字件仅在系统列待办；原办理人停用时仍由其他经办人可查询处理，不丢失。

提醒天数、发送时刻及业务时区为默认配置提案，不代表已经逐条确认。注册待审通知管理员、审核结果通知申请人；密码重置使用一次性流程，不能发送原密码。

上传、识别、邮件、备份失败分别显示和重试。邮件接口超时可能已送达，保留状态并使用可用的去重机制，不能宣称跨外部服务绝对不会重复送达。失败不得改变已确认交接事实。

邮件通道已单独选定 Gmail API，完成独立发信验证；通知事件、待发记录、授权失效和公开配置边界见[邮件与通知设计](email-design.md)。该验证不代表应用通知流程已实现或验收通过。

## 9. 留存与收尾边界

业务历史和已归档原件不随 30 天备份保留期删除；30 天仅指恢复点保留窗口。源数据与备份文件分别管理，恢复须同时验证台账、账号权限和原件关联。

遗失、报废、账号停用、名单停用均保留历史。公开仓库只存源码、文档与虚构示例，真实台账、附件和凭据不提交。

仍待实施前确定的参数仅包括编号格式、文件格式/大小/页数上限、通知具体时间与时区、性能及国内访问验收条件；这些不得阻塞当前业务规则整理，也不擅自作为已确认数值。
