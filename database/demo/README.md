# 演示设备

[inventory.py](inventory.py) 准备一批完全虚构的设备、个人及团队，通过已有的 `gear.create_party` 和 `gear.initialize_asset` 接口建账。使用正常内部编号与权限校验，设备名称、接收对象名称均以“演示”开头，备注保留批次标记。不创建登录账号或交接单，不安装表、函数或触发器，不生成注册或审核邮件任务。

| 设备分类 | 数量 |
| --- | --- |
| 台式电脑 | 12 |
| 笔记本 | 10 |
| 打印机 | 8 |
| 饮水机 | 6 |
| 电插板 | 5 |
| 碎纸机 | 4 |
| 智慧屏 | 3 |
| 其他设备 | 2 |
| 合计 | 50 |

持有情况为库存 20 台、个人 20 台、团队 10 台；其中临时使用 12 台，按准备日期计算已有 4 台逾期。共 6 台故障，分别是库存 4 台、使用中 2 台。接收对象包括 10 名虚构人员和 3 个虚构团队，覆盖本单位、借调、挂职、临时及其他身份。另覆盖未知历史日期、无旧编号、前导零、混合旧编号和明确确认不同实物后的重复旧编号。

## 准备和检查

```sh
python3 database/demo/inventory.py
python3 database/tests/check_demo_inventory.py
```

第一条命令只输出预览，不连接数据库。第二条仅使用一次性本地 PostgreSQL；验证完整批次、重复执行、权限、请求冲突、末条失败时整批回滚以及既有数据保留，已加入 CI。

实际执行需要现有部署者另行核对目标数据库和有效管理员身份。准备 SQL 时必须明确传入 `--base-date`、`--batch`、`--sql-output`，并从私有环境提供 `GEAR_DEMO_ACTOR_ID`。输出只允许放入已忽略的 `.private/`，新文件权限为 600；工具本身不执行 SQL，也不读取数据库连接凭据。不要把实际身份放在命令历史或公开命令示例中。

执行前保存批次 UUID、基准日期和完整输入；重试必须使用相同输入、身份和请求标识。整批在同一事务中执行，成功后保存所有接收对象、设备、初始事件及使用分配的真实 ID，实际清单由 `.env` 中的 `GEAR_DEMO_MANIFEST_FILE` 指向，不提交 Git。事务失败仍可能跳过序列号，不回拨编号。

## 后续清理

本批资料用于开发期间试用，真实设备导入与真实业务验收另行进行。正式切换前，按私有清单导出演示资料，再核对届时的流转、单据、附件和提醒等全部关联；若已被真实业务引用，先处理依赖，不能只按名称或备注批量删除。

当前没有面向用户的演示删除入口。事件历史具有追加式保护，清理工具须按正式切换时的表结构编写，并在用户授权后维护执行，保留真实账号、真实业务和其他应用。清理不重置全局设备编号，不删除业务 schema；整个设备簿数据库不能作为演示批次整体清空。
